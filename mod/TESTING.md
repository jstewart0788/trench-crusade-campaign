# Testing the stripped table in Tabletop Simulator

Nothing in this directory has been loaded in TTS yet. The build was validated offline only
(syntax, GUID cross-references, pack/unpack round-trip), so this walkthrough is the sign-off.
Expect to tune two HUD numbers (step 6) and possibly the Table Theme panel position (step 4).
Step 10 is the sign-off for the second strip (TC-023s).

## 0. Build and install

```
pnpm mod:build      # writes mod/build/trench-crusade.json (about 2.9 MB)
pnpm mod:install    # copies it to ~/Library/Tabletop Simulator/Saves/TrenchCrusade-dev.json
```

Start TTS, create a single-player game, then **Games > Save & Load > TrenchCrusade-dev**.

## 1. Load

- The save loads with no red error lines in the chat/console. Open the console (`~`) and
  check for `error` / `attempt to index a nil value`. Any script error here is a defect in the
  strip; copy the line verbatim.
- Chat shows `Trench Crusade Table (dev) - LCT base 1.12.1` after ~3 s.
- The splash panel ("TRENCH CRUSADE TABLE", patch notes with two bullets, Red / Spectator /
  Blue buttons) is up. Pick **Red**.
- The table surface has no mission-matrix bags, no card decks, no PDFs on the shelf, no link
  tiles at the top-right edge, no "Reinforcements and Reserves" boards behind the hand zones.
- Notebook tabs: "Gaming instructions" (rewritten), "Credits" (upstream attribution, kept)
  and "Trench Crusade content" (what TC-014/017 added and where it is).

## 2. Start menu (the object at x≈52 behind the Red side)

Since TC-023t the Start Menu draws **no** buttons (it only owns the table theme and terrain
pass-through). No GAME MODES, deployment picker, Clear Table, START GAME, or Next Phase /
Pass Turn button. The mat stays at 60" x 44". If any of those render, the build is stale.

### Measured in the live game (2026-11-04, `scripts/tts_exec.py` over the External Editor API)

These are the facts the layout is built on; the scripts re-measure the first three at load.

- **Tile faces.** `b91983` at scale (6,1,6): `getVisualBoundsNormalized().size` =
  (16, 0.2, 12), centre 0.1 above the object; `getBoundsNormalized()` (collider) =
  (16, 0.3, 12), centre 0.15 above. `4ac9e3` at scale (4,1,4): visual (10.667, 0.2, 8),
  collider (14.127, 0.2, 8). So both faces are local x -1.333..1.333 by z -1..1 - the 4:3
  board image, although `CustomTile.Stretch` is true in `mod/save.json` (the Custom Tile
  page's "If the source image is stretched to make for a symmetrical tile" did not hold) -
  and the mesh spans local y 0..0.2: **the pivot is the bottom face**. Every widget placed
  at y 0.12-0.15 sat inside the slab and never rendered, which is what the first TTS session
  saw (seven label-less stubs poking out of the 1700-wide tracker buttons past the tile's
  edges, nothing at all on the importer). Widgets at y 0.30 render; the scripts now put them
  at the measured top + 0.1.
- **Width unit.** A button of width 900 spans two thirds of the 16-unit importer face, so
  width = local units x 500 (the API only says "How wide the button will be, relative to
  the Object"). The LCT dice mats (`acae21`, scale 3.75) agree: their 160/110/80-unit
  widgets sit 0.29 and 0.2 local units apart.
- **Height unit.** Not the width unit. 170-tall tracker buttons at a 0.26 pitch read as
  separate rows (so at least 654 per local unit) while 210-tall ones measured about 0.38
  local in a screenshot (548); the overlap checks use 650. The API floor matters more:
  "The minimum width/height is 60. Any lower number (besides 0) will appear to be 60" -
  25-tall member rows at a 0.055 pitch rendered as one blob, 40-tall rows at 0.14 did not.
  Rows are now 60 tall at 0.14.
- **Inputs.** Width 900 / height 100-130 / font 70-100 at button scale 1 read well at tile
  scale 6 (do not copy the dice mat's scale-0.1 input; that is a tiny number box). Height
  follows the API's "(font_size * # of lines) + 23".
- **The mat.** Object `4ee1f2` "matObjSurface" (Custom_Model): `getBounds()` centre
  (0, -0.5, 0), size (60, 2.9, 44) - playing surface x -30..30, z -22..22, top at y 0.95.
  The 136x199 tile `28865a` is the table, not the mat. The old fixed anchors at z = +/-44
  put a real import (YPFTBM) at (13.8..18.8, 0.9, 44) where nobody saw it.
- **Spawn structure.** A default-model spawn carries the Gannel figure as a child
  (`m1` has one attachment with the Gannel mesh URL); whether it renders is still a visual
  check.
- **Final numbers confirmed in TTS** by pushing the new layout through `editButton` /
  `editInput` on the live objects and reading `getButtons()` back (importer: controls at
  local x 0.56, y 0.40, rows at x -0.80 pitch 0.14; tracker: y 0.30, rows 0.27 apart).

### Orientation and sizing

- The save loads into the host camera at x≈-31 looking toward +x (`CameraStates[0]` yaw
  90; both hand zones sit at x=-42 with rotY 270; the LCT Start Menu at x=52 is rotY 270
  for the same reason). The importer tile at (-22, 1, 0) is 20" in front of that camera
  with `rotY: 270` in `mod/save.json`; its widgets keep rotation `{0,0,0}` (label top at
  local -z), so they read upright from there. **If the panel is still rotated, change
  `rotY` on object `b91983` in `mod/save.json` by +-90**; the Lua positions are local and
  follow the tile.
- Geometry lives in `LAYOUT` (importer) and `BUTTONS` (tracker): rows/cols in local units
  for the measured 4:3 face (`REF`), width/height/font in widget units; at load
  `geomFromBounds` stretches the layout to whatever face the object reports and lifts it
  above the measured top. Each object prints one line to the host chat on load, e.g.
  `[Warband Importer] visual 16.00x0.20x12.00 scale 6.00,1.00,6.00 half 1.333x1.000 top
  0.30 y 0.40 units/local 500 first title(0.56,0.40,-0.91) last status(0.56,0.40,0.62)` -
  read it back if anything renders wrong, and `getObjectFromGUID("b91983").call("relayout")`
  (or `4ac9e3`) re-measures and rebuilds without a reload. The knobs: `UNITS_PER_LOCAL`
  (uniformly wrong size), `HEIGHT_UNITS_PER_LOCAL` (rows colliding), then the per-widget
  values; `pnpm mod:test` keeps every widget on the face and non-overlapping.

### Walkthrough

- The **Warband Importer** tile (dark charcoal 16"x12", the Scripted Table's board image)
  shows two blocks. Down the viewer's left: a gold **WARBAND IMPORTER** label; the **API
  base URL** input (`https://tc.rynfin.org (hosted roster tool; type http://127.0.0.1:3001 for a local `pnpm dev` API)`); the larger **Warband code** input; **Colour:
  mine**; **Bind**; a green **Import**; and a status box (`Start the API, type a code, press
  Import.`). The right half is empty until a warband is imported. Click into the code
  field: a caret appears and typing lands in it.
- Seated as **Red**, type `NA-TEST-01`, press **Import**. Status goes `Fetching
  https://tc.rynfin.org (hosted roster tool; type http://127.0.0.1:3001 for a local `pnpm dev` API)/api/tts/warband/NA-TEST-01` (wrapped), then `Test warband: spawned
  6 model(s) for Red.` The server's terminal logs one `GET ... 200`. Six models land **on
  the mat** along Red's edge: a row of six at z=19 (3" inside the +z edge), x from -6.25 to
  6.25 (2.5" apart, centred on the mat), y 1.95, facing -z, bases tinted toward red; a
  seventh would start a second row at z=16.5, toward the centre. Hover one: the tooltip
  shows the Lieutenant's description (`Lieutenant` header, `Mov 6"/Infantry  Rng +2  Mel
  +2  Arm -1  Base 32mm`, keywords, equipment, abilities); the GM Notes field (right-click
  > GM Notes) carries the full rule text. Every model carries the tags
  `tc-warband:NA-TEST-01`, `tc-member:m<n>` and `tc-spawned` (right-click > Tags).
- Member rows fill the right column top to bottom, one per member: `1. Lieutenant` ...
  `6. Shocktrooper`; hover a row for the full label (`[default model]` or `[plain base]`).
  A warband with more than 14 members shows the first 14 and says so in the status. The
  figures are Gannel's Model Corner meshes attached to a Gannel's 32mm base; a member whose
  unit has no entry in `data/tts/models.json` spawns the bare base with the same name,
  description and tags.
- **Bind**: click `2. Yeoman` (the row turns gold), press **Bind** (status: `Red: pick up
  the model that becomes Yeoman (Bind again to cancel).`), then pick up any other object - a
  model pulled from a bag, or a die for the smoke test. Its name, description, GM notes and
  tags become the Yeoman's (`tc-bound` instead of `tc-spawned`), the spawned default Yeoman
  for that member is deleted, and status reads `Bound Yeoman to <its old name> (default
  model removed).` Pressing Bind a second time before picking anything up cancels. Picking
  up the importer tile itself never binds.
- **Re-import**: press **Import** again with the same code. The Import button becomes a red
  **Replace** and a grey **Cancel** pair and the status reads `NA-TEST-01 is already on the
  table: replace 5 spawned model(s) and re-bind 1 of your own?` **Cancel** restores Import
  and leaves the table alone. **Replace** deletes the five spawned models, keeps the object
  you bound (its text is refreshed from the new payload), fetches again and spawns only the
  five members without a bound model: `Test warband: spawned 5 model(s) for Red, re-bound 1
  of your own.`
- **Colour**: the button cycles `Colour: mine` -> `Colour: Red` -> `Colour: Blue` -> ... ->
  `Colour: Brown` -> `Colour: mine`. With `mine`, the seat of whoever presses Import is
  used. Switch to **Blue**, import again (Replace, or a second code): Blue's models land
  along Blue's edge (z=-19, facing +z, rows growing toward the centre, blue-tinted bases).
  Any other colour, or a spectator importing with `mine`, gets a grid 8" in front of the
  importer tile. With a fixed colour chosen, the grid and tint follow that seat regardless
  of who clicks. If the mat has been moved or rescaled (Start Menu modes), the rows follow
  it: the importer reads `4ee1f2`'s bounds at import time, or the first flat 50-70 x 34-54
  object if that GUID is gone, and only then the measured default.
- Errors to provoke: stop the server and Import (`Request failed: ...`); a wrong code
  (`HTTP 404 for XYZ`); edit the API field to a page that is not JSON (`Response is not
  JSON.` or `Rejected: unsupported export version ...`). None of these spawn anything. A
  value typed into a field and never deselected still counts: Import reads the widgets
  directly (`self.getInputs()`) before fetching.
- Save and reload: the API field, code and colour choice persist (object script state);
  the member list does not (re-import to repopulate it).
